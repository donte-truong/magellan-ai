## What the successful run shows

- **Depth:** 24 tier-1 nodes and 9 tier-2 nodes; 10 of 34 planned tasks finished before the document cap, with 15 tier-1 and 9 tier-2 tasks still pending. Fair scheduling gave every tier-1 branch a turn before deepening. Corroboration works: the BCM2712 edge has three claims from three sources (confidence 0.85).
- **Planner quality:** queries were specific and source-typed (BOM lists, teardowns, SEC Form SD, FCC filings, foundry queries, `site:raspberrypi.com`), and relation types rotated between upstream inputs, manufacturer or facility, and supplier.
- **Gates held:** 75 candidates were rejected (28 predicate or direction, 22 scope, 12 span not found, 10 entailment, 3 disconnected) and only 1 model output was unusable.

## Coherence problems, in priority order

1. **Accessories treated as parts.** An Indian accessory buying guide contributed most tier-1 rows: cases, HATs, cameras, GPS modules, starter kits, keyboards, cables are PART_OF the product with product scope. The spans are verbatim and the verifier passed them, so the failure is semantic: "accessory for" is not "part of". Needs an explicit exclusion in extraction and verification prompts (accessories, kits, bundles, and compatible add-ons are not components), plus a scope rule that a kit containing the product cannot be part of it.
2. **Wrong kinds.** "Raspberry Pi Case for Raspberry Pi 5" became a facility; "Raspberry Pi 5 8GB" became a component of a desktop kit. Kind guidance was tightened after the run; a verifier check on kind should follow.
3. **Duplicate entities.** Four case nodes (`Official Raspberry Pi 5 Case`, `Official Raspberry Pi Case for Raspberry Pi 5`, `official Raspberry Pi case`, `case`), two M.2 HAT+ pairs, `RP1` versus `RP1 I/O controller chip`, and `BCM2712` versus `Broadcom BCM2712`. Deterministic resolution behaved as designed (no wrong merges), but `entity.review_needed` never fired because bare-name variants do not carry identifiers. The review event needs a near-duplicate signal (shared part number, one label contained in another within the same kind) that flags without merging.
4. **Retail and blog sources.** No first-party page was read for the root task; the official documentation only appeared for the M.2 HAT+. Source-type preference from the planner is not yet applied when ranking search results.
5. **Manufacturing versus design.** "Engineered by Broadcom" became MANUFACTURES. The prompt already says designer is not manufacturer; the verifier should be asked explicitly whether the span states physical manufacture.

## Fixes made during the session

Bounded Retry-After handling for 429s; video and social hosts skipped in research search; a task continues past one unusable document instead of being abandoned; planner output room raised for reasoning models; `OPENROUTER_REASONING` setting to disable or bound hidden reasoning; kind guidance in the extraction prompt.

Remaining coherence problems, in priority order:

2. **Software as components**: the CYW43455 branch turned firmware and driver files (`brcmfmac43455-sdio.bin`, `brcmfmac`) into parts. The extraction and verification prompts need an explicit exclusion for firmware, drivers, and software.
3. **Verifier misses**: `Broadcom BCM2712 PART_OF ARM Cortex-A76` (reversed, from a spec table) and `LPDDR4X RAM PART_OF Raspberry Pi 5` cited to a sentence about the PMIC both passed entailment. A kind and direction check in verification, or a stronger verifier model, would catch these.
4. **Node cap binds first now.** With 29 tasks queued at tier 2, `max_nodes` (default 50, contract maximum 150) is the limit to raise for deeper graphs, once duplicates are under control so the cap is not spent on variants.

## Third DeepSeek run, after the coherence fixes (`0c576b8`)

Same model and settings, with `max_nodes` 100 and `max_documents` 60 so the node cap would not bind first. The coherence fixes: name variants resolve through recorded part numbers and maker prefixes, near-duplicates within a kind emit `entity.review_needed`, firmware and driver files are rejected as parts, and the verifier is told to fail reversed directions, unnamed subjects, software, accessories, and wrong kinds.

What the fixes did: the review signal now fires on bare-name variants (`Broadcom VideoCore VII GPU` versus `VideoCore VII`, `GPIO header` versus `40-pin GPIO header`), a maker-prefixed variant merged on evidence (`VideoCore VII GPU` became an alias), no software artifact reached the graph, and the one reversed relation seen earlier did not recur. Verification still passed a claim that a "MIPI-CSI Connector" is part of "MIPI CSI-2 Camera Ports"; the verifier remains the weakest gate.

The regression is not the fixes: it is the root task's first plan. Run two's root plan searched `site:raspberrypi.com`; run three's asked about PCB manufacturers and SEC filings, found nothing usable, and the one relevant page was a reseller spec sheet whose feature list became seventeen tier-1 "components". Interface features (ports, slots, radio standards) then consumed three searches each with `unresolved` outcomes until the search cap was gone. Two conclusions:

1. **Interfaces are not parts.** The extraction and verification prompts need the same exclusion that accessories and software now have: ports, slots, connectors, headers, and protocol names (USB 3.0, Wi-Fi 6, Bluetooth 5.2, Gigabit Ethernet) describe interfaces, not components, unless a specific part is named. A cheap code gate on those words would stop the search budget bleeding into them.
2. **The root task deserves a fixed opening.** One run's quality depends on whether the planner happens to search the maker's own site first. Seeding the root task with a first-party query (`site:<company domain> <product>` and the product brief or datasheet) before the planner's queries would make the opening deterministic, and the source ranker already prefers those hosts.
